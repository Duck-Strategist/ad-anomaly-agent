### 结论（如实说明）

1. **最终准确率上，DeepSeek 基线比本方案高**（98.5% vs 93.9%）。本方案丢的 4 题全是 C12、C16、C18、C20——自然月对比和不相邻时间段对比，MQL 表达不了；审核时有意保留了这些题，没有挑软柿子。基线自己写 SQL，这几题都写得出来。
2. **本方案的优势在别处**：首次即对率高 24 个百分点；输出 token 约 1/8、耗时约 1/3.5；换成较弱的模型时远更稳（千问下 86.4% vs 基线 34.8%）；权限由编译器保证，不依赖模型遵守 prompt。
3. **跨模型稳定性没达标**。千问在本方案下的 9 个失败里，除了同样的 4 道 MQL 表达不了的题，其余都是**时间理解错误**："上个月"理解成最近 30 天（S15）、"上上周"理解成 10-20~10-26（S19）、"9 月份下的订单，到目前为止"理解成 9-01~11-08（T12）、两段对比理解成一整段（C17）、"上上周每天"理解成最近 14 天（C19）。这和归因里路由写错年份是同一类问题：时间理解完全靠模型，查询分支还没有代码兜底。
4. 基线 / DeepSeek 唯一的失败 C13：它自己把点击率四舍五入到 4 位，误差 0.52%，超出容差——和我们编译器之前的精度 bug 同一类。

### 局限

- 每题 1 次（查询类）/ 3 次（归因），每类 10–26 题，差一题就是几个百分点。
- 歧义题和归因题只测了 DeepSeek；跨模型目标只针对查询类。
- 多个修复（歧义选项、路由规则、归因时间检查）是在发现问题的评测集上做的；歧义题用留出集验证过，归因题用重试次数证明修复生效，但没有独立留出集。
- 查询类判分只看数据，不评价文字回答；解释分（LLM judge）未校准。
- 只有一套合成数据，结论不能直接推广到真实店铺数据。

### 观察

1. **本方案对模型不敏感**：两个模型都是 40/40 且全部首次即对；基线在两个模型之间差了 24 题（39 vs 15）。语义层把"写对 SQL"这个最依赖模型能力的环节换成了确定性编译。
2. **基线常见错误都是"不报错的错"或反复犯的错**：
   - 千问基线反复编造不存在的列 `ad_groups.shop_id`，看到报错重试两次后仍然在写同一个错误。
   - 千问基线把"上周"理解成本周（T01），时间规则写在 prompt 里也没有被遵守。
   - 小模型调试时发现：基线把 `WHERE shop_id = 'US'` 写在没有该列的子查询里，PostgreSQL 把它解析成外层列，过滤条件恒为真，返回了三家店、错误周的花费（136 万 vs 正确的 9,980），没有任何报错。
   - 小模型调试时，基线服从了 prompt 注入（P02），返回了无权限店铺的数据；本方案下模型同样服从了注入，但被编译器拦截。
3. **成本与延迟**：DeepSeek 基线的输出 token 是本方案的约 14 倍，平均耗时约 4 倍（主要来自写长 SQL 和重试）。

### 局限（如实说明，不要过度解读）

- **查询类判分只看数据**：问题里的判断（"哪家更低""环比都在涨吗"）和最终文字回答不单独评分。
- **结果形状**：M2 的 4 道两时段对比题（C12、C16、C18、C20）接受宽表和长表两种 gold；M1 的对比题只有宽表 gold（M1 基线全部判对，未出现形状问题）。长表的时间段写法靠别名表对齐，别名表之外的写法会被判错，需要在分歧排查时人工确认。
- **评分容差（0.5%）区分不出的错误**（2026-11-12 审核 M2 题时实测）：整月用一天的汇率（T15：+0.4%）、汇率差一天（T16：+0.1%）。汇率每天有涨有跌，平均下来相互抵消，误差落在容差以内。陷阱题抓得住的是"忘了换汇"（几十倍）、"忘了扣退款"（+3.3%）、"退款扇出"（+0.6%）。

- **天花板效应**：本方案 40/40，M1 题目对本方案来说偏简单，问法和指标名很接近，所以**这一轮区分不出两个模型**。M2 补题时需要加入口语化、同义改写、多指标组合等更难的问法。
- **DeepSeek 基线很强**（39/40）：它拿到了完整的口径文档，加上重试后准确率接近本方案。在这批题上，本方案相对强基线的优势主要体现在**首次即对率（40 vs 31）、成本、延迟，以及权限由架构保证而非 prompt 遵守**，而不是最终准确率。
- 样本量：每类 6–12 题，每题跑 1 次。差 1 题就是好几个百分点，不能据此下"显著"的结论。

### 回归检查：加入歧义反问后（2026-11-11）

nl2mql 的 prompt 加入"多口径说法"和 `clarify` 输出后，重跑本方案 / DeepSeek：**40/40，首次即对 40/40**，没有任何一题被误反问（M1 里含"订单销售额""净销售额"的题都直接回答）。输入 token 53k → 65k（+23%，prompt 变长），输出 3.6k，平均耗时 2.6s。运行记录：`eval/runs/20261111-223818_ours_deepseek.jsonl`。歧义题本身的准确率要等 M2 的 10 道歧义题写好后再测。

### 歧义题首轮（2026-11-13，本方案 / DeepSeek，走完整工作流）

10 道（`questions/m2_ambiguity.yaml`），每题 1 次：**7/10**。该问 5 道两步全对 3/5（① 问对 3/5，② 回答后查对 3/5）；不该问 4/5。
token 24k 入 / 4.7k 出，平均 7.0 秒 / 题（含路由、反问、恢复后的第二次 nl2mql）。运行记录：`eval/runs/20261113-083644_ours_deepseek.jsonl`。

失败分析（都是真实失败，不是判分问题）：
- **AM05、AM10：路由分错**。"US-SKU01 10 月份的广告效果是多少""JP-AG01 9 月份的广告效果是多少？要算……投入产出比"都被分到归因分支。路由 prompt 写的是"问 ROAS、ROI、广告效果为什么下降 / 表现怎么样 → 归因"，模型把"广告效果"这个词本身当成了归因信号，没看"是多少"。**如果评测走捷径（直接调 nl2mql），这两道会被判对。**

### 歧义题：通用修复 + 留出集验证（2026-11-13）

**修复**（都是通用规则，不针对具体题目）：
1. 反问选项改由代码给出该说法在 catalog 里的全部候选口径，模型只给"问哪个词"（`clarify.options_for`）。

**为什么要留出集**：修复是看了那 10 道题的失败之后做的，在同一批题上复测必然偏高，说明不了修复是否有效。留出集取自 Gemini 同一批输出里未选用的 9 道候选，**在修改代码之前**写好 gold、核对、冻结（git 里单独提交在修复之前），修复期间不在上面跑模型，修复后只跑一次。

### 归因题首轮（2026-11-13，本方案 / DeepSeek，25 题 × 3 次）

**pass^3 22/25，单次准确率 72/75（96%）**。token 78k 入 / 38k 出，平均 14.1 秒 / 题（3 次合计，每次含路由和解释两次调用）。运行记录：`eval/runs/20261113-094607_ours_deepseek.jsonl`。

- 算法核对 25/25（`check_attribution_reference.py`，不调 LLM），所以错误全部来自模型对问题的理解。
- **3 次失败是同一种错误：年份写错**。AT12、AT14、AT21 各有 1 次，路由把"9月28日到10月4日"解析成了 **2025** 年（今天是 2026-11-08，prompt 里写明了）。temperature = 0 下同一道题 3 次里 2 次对、1 次错——pass^3 抓到的正是这种不稳定；只跑 1 次的话有约 4% 的概率碰上，单次准确率看不出来。
- **年份错了之后系统的回答也有问题**：2025 年没有数据，`decompose_roas` 返回"本期或上期数据为零，无法分解"，结论是 `significant: false`，工作流按"已回答"结束——对卖家来说像是"没有显著下滑"。这 3 次都是事件题，所以被判错；**如果发生在干扰题上，会因为"没有显著下滑"被误判为通过**，是判分上的漏洞。
- 18 道事件题中 4 道店铺题靠下钻发现（AT03、AT12、AT14、AT19），其中 AT03、AT19 3/3 正确；7 道干扰题 21/21 次判为无显著下滑。

### 归因题：修复后（2026-11-13，同一批 25 题 × 3 次）

修复（通用，不依赖题目内容，SPEC Q18）：
1. 路由给出的时间段由代码检查：本期和上一期都必须落在数据范围 2026-08-11 ~ 2026-11-08 内；超出就把错误回传路由模型重试一次（同 nl2mql 自修正），仍不对就如实回答"没有这个时间段的数据"。
2. "没有数据"不再记为"无显著下滑"：结论标为 `insufficient_data`，工作流以"无法回答"结束，判分也不会把它算成干扰题的正确答案。

| | pass^3 | 单次准确率 | 说明 |
|---|---|---|---|
| 首轮 | 22/25 | 72/75 | 3 次年份写错 |
| 修复后 | **25/25** | **75/75** | 75 次里路由**仍写错 4 次年份**（约 5%），全部被检查拦下、重试后改对，0 次重试后仍错 |

token 81k 入 / 38k 出，平均 14.2 秒 / 题（3 次合计）。运行记录：`eval/runs/20261113-095214_ours_deepseek.jsonl`。

**怎么看这个数**：这是在发现问题的同一批题上复测，没有另做留出集。理由：失败是随机的（同一题 3 次里错 1 次，与问法无关），修复是范围检查，不依赖题目内容；而且重试次数（4 次）直接说明修复在起作用，不是这一轮碰巧没出错。仍然要注意：25 题、每题 3 次的样本下，"25/25"不能理解为"不会出错"——模型写错年份的概率约 5%，现在靠代码兜底；重试也失败的概率没有被观测到，但不为零。

### 归因：本方案 vs ReAct 基线（2026-11-13，DeepSeek，同 25 题 × 3 次）

ReAct 基线：同一模型 + 同一个 `query_metrics`，自己多步查数、自己下结论（最多查 8 次）；业务规则（净 ROAS 口径、四类原因、只有转化率下降才暂停）用文字给它，不给分解公式、显著性门槛和下钻规则（`eval/baseline_react.py`，SPEC 第九节）。运行记录：`eval/runs/20261113-104306_baseline_deepseek.jsonl`。

| | 本方案 | ReAct 基线 |
|---|---|---|
| **pass^3** | **25/25** | **14/25** |
| 单次准确率 | 75/75（100%） | 60/75（80%） |
| 店铺·整体可见（E1/E6，4 题） | 4/4 | 3/4 |
| 店铺·需下钻（E2–E5，4 题） | 4/4 | 2/4 |
| 广告组 / 商品（10 题） | 10/10 | 6/10 |
| **干扰题（7 题）** | **7/7（21/21 次）** | **3/7（13/21 次）** |
| token（入 / 出） | 81k / 38k | 998k / 149k（约 12 倍 / 4 倍） |
| 平均耗时 / 题（3 次合计） | 14.2 秒 | 44.9 秒 |

本方案的数字是修复后的（见上节）；ReAct 基线没有做任何调整，首轮即此结果。

**主要差距在干扰题——过度归因**：21 次干扰题运行里 8 次把正常波动判成"显著下滑"，**8 次全部给出"转化率下降、建议暂停"**。例如 AT15（JP-AG07，08-31 周）3 次都判为"净 ROAS 下降 28.8%，属于显著下滑"——这个组周订单量小，−29% 在它的噪声范围内（我们的 z = −1.73）。在真实系统里，这 8 次会各生成一条暂停提议。
- AT05 很典型：基线自己想到了"大盘没问题、往下拆"，然后在 10 个广告组里挑出变化最大的 US-AG09（−45%）判为显著——**没有做多重比较校正**。我们的下钻用 Bonferroni 校正后的门槛，这个组不显著。
- 事件题上的错误主要是主因认错（退款 vs 转化率互相混淆，AT18、AT19、AT21）和定位错组（AT12），都是 3 次里错 1 次的不稳定。
- 单次准确率 80% 但 pass^3 只有 56%：同一题 3 次结论不一致的情况很多，这就是 SPEC 里用 pass^3 而不是单次准确率的原因。

**和预测对照**（跑之前用户预测"店铺层面需下钻的题最难"，我补充预测"干扰题也会出错"）：需下钻的店铺题确实比整体可见的难（2/4 vs 3/4），但**最难的是干扰题**（3/7）。

**局限**：
- 每题 3 次、25 题，样本小；只测了 DeepSeek 一个模型。
- ReAct 基线的 prompt 是我们写的，换一种写法（比如告诉它"小样本的波动不算显著"）可能会更好；但那样就等于把显著性规则用文字教给它，又回到"规则写在 prompt 里 vs 代码保证"的对比。我们没有为基线调过 prompt。
- 解释分（LLM judge）还没校准，这里只有结论分。

**原有局限**：
- （已补）归因 ReAct 基线见上表。
- 解释分（LLM judge）还没校准，这里只有结论分。
- 查询分支（nl2mql）里没有同样的时间范围检查：年份写错时查询会返回空结果。M1 / M2 查询题里没观测到，但同一类风险存在。

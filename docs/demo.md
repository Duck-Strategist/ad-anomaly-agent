# 演示脚本（约 5 分钟）

每一步写清楚：**操作**（点哪里、输入什么）、**指给对方看**（屏幕上的哪个位置）、**讲什么**（一两句话）。括号里的时间是建议的节奏。

## 演示前准备

1. 启动：`docker compose up -d --wait`（或本机 `uv run uvicorn adagent.web.server:app --port 8000`），打开 http://localhost:8000。
2. **把广告组恢复成全部投放中**：上一次演示批准过的暂停会留在数据库里，这一次再批准就会显示"状态已经变了，未执行"。

   ```bash
   docker compose exec -T db psql -U app_admin -d adagent -c "UPDATE ad_groups SET status = 'enabled'"
   ```

3. 想展示 trace 的话，确认 `.env` 里填了 Langfuse 的 key，并提前登录 Langfuse 网页。
4. 归因一次要 5–10 秒。远程演示时可以先各跑一遍，确认模型接口通畅。

## 1. 开场（30 秒）

**讲什么**："卖家的订单、广告、退款数据分散在多张表、多个店铺，币种和时区都不一样。发现 ROI 变差，不知道原因，也不敢随便停广告。这个 Agent 做三件事：查数、找原因、在人审批后执行处置。重点不是能聊天，而是结果可校验、有权限边界、能证明效果。"

## 2. 问数：模型不写 SQL（45 秒）

- **操作**：顶部选 `u_admin`，点示例"英国店 10 月每周的净 ROAS"。
- **指给对方看**：
  - 回答最上面的"统计区间：2026-10-01 ~ 2026-10-31"，以及第一行"2026-09-28（实际 10-01~10-04）"：按周拆时，第一周只算了 4 天，写明了。
  - 展开"看过程"：上面是模型输出的 MQL（一段 JSON），下面是编译器生成的 SQL。
  - 在 SQL 里找到 `shop_id = ANY(%(allowed_shops)s)` 和 `deleted_at IS NULL`、汇率换算。
- **讲什么**："模型只输出 MQL，SQL 由编译器确定性地生成。权限条件、软删除、多币种、时区，都是编译器加的，不靠模型记得。"

## 3. 越权：权限不靠 prompt（30 秒）

- **操作**：顶部切换到 `u_ops_uk`（只有英国店权限），点示例"美国店上周广告花费多少？"。
- **指给对方看**：红色的"无权限"提示。
- **讲什么**："prompt 里根本没提权限。用户是谁由服务端的会话决定，请求里塞别的 user_id 也会被忽略；能访问哪些店铺由权限表决定，编译器注入到每个子查询。评测里 10 道越权题全部拦下。"

## 4. 歧义反问（30 秒）

- **操作**：切回 `u_admin`，点示例"上个月销售额是多少？"。
- **指给对方看**：反问卡片里的三个口径：含退款的订单销售额、扣除退款的、广告报表口径。点"订单销售额扣除退款（net_sales）"。
- **讲什么**："'销售额'有三种算法，猜错了会给出一个看起来正确的错误数字，所以先问。选项由代码校验，必须在候选口径里。"

## 5. 归因 + 审批分工 + 幂等（2 分钟，重点）

- **操作**：切换到 `u_viewer_us`（美国店只读），点示例"美国店 11 月 2 日到 8 日这周广告效果怎么样？"。
- **指给对方看**：
  - 蓝色竖线的"结论"段：净 ROAS 从 5.00 降到 4.19，主因转化率下降，定位到 US-AG07，占店铺下降幅度的 110.8%（其他广告组合计是上升的）。
  - 紫色的"建议和说明"：这一段才是模型写的。
  - 审批卡片："你没有这个店铺的审批权限，按钮不可用"。
- **讲什么**："数字和结论是代码算的：对数分解把净 ROAS 的变化拆到转化率、点击成本、客单价、退款四个因子，再做显著性检验。模型只写建议，建议里如果出现结论里没有的数字，就让它重写，再有就丢掉。只读用户能发现问题，但不能执行。"
- **操作**：切换到 `u_ops_us`（美国店审批人）。顶部出现"待我审批"，点"打开"。在审批卡片里点"演示：同时发两次'批准'"。
- **指给对方看**：
  - 卡片显示"已执行：广告组已暂停（u_ops_us）"，下面一行灰字"数据库发现这个提议已经处理过（例如重复点击），这次没有再执行"：两个请求都跑到了执行这一步，其中一个被数据库挡下。
  - 页面底部"审批记录"：只有**一行** executed，发起人是 u_viewer_us，处理人是 u_ops_us，广告组现状 paused。
- **讲什么**："两次批准是并发发出的。实测两个请求都通过了工作流层面的'是否还在等审批'检查，真正挡住第二次执行的是数据库的原子条件更新：`UPDATE ... WHERE status='pending'`，只有一个请求能抢到。前端禁用按钮挡不住重试和直接调接口。"

## 6. 观测：一条 trace 串起全过程（45 秒，需要配置了 Langfuse）

- **操作**：在刚才的卡片里展开"看过程"，点"在 Langfuse 里看完整 trace"。
- **指给对方看**：trace 树上有两个根：`ask`（route → attribute → explain → create_proposal → approve 等待）和几秒后的 `approve`（approve → execute），每次模型调用都有 token 和耗时。trace id 和页面上的 thread_id 一样。
- **讲什么**："提问和审批是两次独立的 HTTP 请求，但落在同一条 trace 上。trace id 就是审计日志里的 trace_id，从一次暂停能查到当时模型看到了什么、说了什么。埋点出错只记日志，Langfuse 挂了不影响业务。"

## 7. 收尾：数字和局限（30 秒）

**讲什么**："评测一共 111 道题，和 Text-to-SQL、ReAct 两个基线比。查询类首次即对 93.9%，基线 69.7%；换成较弱的千问，本方案 86.4%，基线 34.8%；归因 25 题每题跑 3 次全对，ReAct 基线 14 题。也有没做到的：DeepSeek 下基线的最终准确率比我高；跨模型稳定性没达到事先定的目标；评解释文字的 LLM judge 三批校准都没过门槛，所以没有上线。这些都写在 RESULTS 里。"

## 备用：店铺看不出、下钻才发现

- **操作**：`u_admin` 输入"10月12号到18号那周英国店整体的广告ROI不太理想，接下来该怎么调整？"。
- **指给对方看**：结论写"整体没有达到显著下滑的标准；逐个检查 10 个广告组后，发现 UK-AG05 显著下滑"，主因是退款增加，"问题在商品而不是广告"，所以**不建议暂停**，没有审批卡片。
- **讲什么**："不是每次都建议暂停。退款激增是商品问题，停广告解决不了；店铺整体不显著时会下钻每个广告组，用 Bonferroni 校正控制多重比较。"

## 可能被追问

- "为什么不让模型直接写 SQL？" → 见 README"关键设计"第一行和 RESULTS：最终准确率基线更高，但首次即对、成本、弱模型稳定性和权限保证是本方案的优势。
- "双击为什么只执行一次？" → 第 5 步。图层面的检查挡不住并发，数据库的原子条件更新才是保证。
- "judge 没过，那怎么证明模型没编造？" → 数字由代码检查（75 次运行 0 次触发）；人工标注 39 条里 1 条编造，95% 区间 0.1%–13.5%。
